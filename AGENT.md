# Instructions for Working on the Project

DO NOT EDIT this file, if it is necessary report all reasons to the user without touching this file.

## Coding rules

The code inside the project has to be kept maintainable, expandable, decoupled, clean, and self-explanatory. No comments are allowed inside any script (except for the one in the AI-created script chapter below); if the code is not self-explanatory, then it is not good code to write. The code should follow (not strictly) all the SOLID principles, without overengineering it. It should follow DRY (don't repeat yourself) too, without having duplicated code inside multiple scripts / methods.

The code should follow the KISS (Keep it simple) principle, preferring simple solutions over complex and overengineered ones.

Prefer more verbose coding over unclear code statements and scripts.

If present, use the skill PONYTAIL.

## Git Commit Policy

No commit should be executed unless the user specifies it. Before committing, always show the user a commit draft. The commit should avoid walls of text, preferring clear, short lines.

## Code styling

The code styling should follow the scripts already present in the project, following their good practices and the components created by human operators. If no components were created by humans, skip this phase. Code written by a human operator has the comment "HUMAN OPERATOR CODE" at the beginning of the file.

## Asset location

Each asset (if applicable) should be imported and used using the folder corresponding to its type.
If no location is present for that given asset, create one to maintain order inside the project's repository.

## Practices to follow before editing

1. Every file you design should respect the coding rules and practices explained above. You MUST use the skill Ponytail if present.
2. If the user's request is not clear, has points that are not described, or lacks some information, you should ask for clarification using the ask tool. When uncertain, prefer to ask. Always provide a recommended choice.

## Frontend Practices

1. Design & Code Standards: Always apply high-quality frontend principles. When available, invoke relevant skills (e.g., Taste, Impeccable) to refine layout, typography, and UX.
2. Clarification First: If any information is missing (design direction, product requirements, styling constraints) or requirements are unclear, ask the user for clarification before assuming. Prefer asking over guessing.
3. Quality & Anti-Slop Review: After completing frontend changes, evaluate the output against anti-slop guidelines. Summarize the review findings and any trade-offs directly to the user. Small changes, such as simple typo fixes, minor value adjustments, or straightforward edits with negligible risk, do not require a dedicated code review.
4. When a component alredy exists or it can be found online inside a public, free library, you should report its existance to the user, including whether they should use it in their design.
5. Avoid writing SVGs by hand; prefer icon library.

## Practices after each edit

1. You should run a review of the code written (if present, use the thermo-nuclear-code-quality-review skill) to find possible weaknesses and rules not respected by the code. Report to the user what has been found in the review and wait for their approval before fixing. If the review finds no issues, reassure the user and report the job as done. If no thermo-nuclear-code-quality-review can be found, you should declare it and continue with a normal code review. The review run should be executed only on more complex edits; short fixes and little changes should not trigger a review, as it would just waste tokens on already clean code. Small changes, such as simple typo fixes, minor value adjustments, or straightforward edits with negligible risk, do not require a dedicated code review. When in doubt, prefer performing a code review if the change could introduce bugs or affect existing behavior. If a code review is required, follow the existing code review rules: execute it only once per set of changes, report the findings to the user, and wait for approval before fixing any issues found.
2. You should explain to the user what has been done, using both a human-understandable explanation and an edited code analysis.
